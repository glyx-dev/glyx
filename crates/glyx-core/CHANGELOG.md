# Changelog

Changes to the native runtime and renderer (`glyx-core`, and the crates it drives: `glyx-renderer`, `glyx-gpu`, `glyx-sysapi`, the vendored `vello`). JS-facing API changes are in `@glyx-dev/react`'s changelog.

## [Unreleased]

### Fixed
- **A closed dropdown, tooltip or shadow could leave its pixels on screen.** Removing an overflowing node only damaged its parent's rectangle, so the part that hung outside stayed painted until something else happened to repaint it; a font menu looked stuck behind the text after it closed. The last drawn bounds of a removed node now count as damage for that frame, and the entry is dropped once the frame is drawn.
- **The caret, the selection and the IME underline of a text field were placed by the default regular font**, whatever the field was drawn in: with a bold, wide or other-family font they drifted off the glyphs (a click landed on one character and the caret showed 12% to the left of it). They are now measured in the font, weight and style the text is drawn in.
- **Variable-font axes are drawn on every renderer.** The CPU renderer's glyph cache now has an entry per axis setting, Vello and the outline path (rotated text) pass the run's normalized coordinates, and Direct2D builds the face with the axis values applied.

### Added
- **OpenType font features.** `fontFeatureSettings` (CSS source, `"'liga' 0, 'tnum' 1, 'smcp' 1, 'ss01' 1"`) joins the family, variable-font axes and numeric weight in one `glyx_text::font_id`; the shaper applies the features, so layout, drawing, ellipsis, accessibility and every renderer agree. The JS measuring calls take them as `features` in their font object, and a rich-text span can set its own.
- **Per-side borders and per-corner radii.** `NodeProps` gains four side widths, four side colours and four corner radii, parsed by V8 and QuickJS and editable in DevTools. A uniform border keeps the old centred single stroke; mixed widths or colours draw four inside bands with corner splits weighted by the adjacent widths, and per-corner radii also apply to backgrounds, shadows, image clipping, child clips and placeholder fills. Borders still take no layout space.
- **Variable-font axes and numeric weights.** `fontVariationSettings` (CSS source, `"'wght' 650, 'wdth' 80"`) and a numeric `fontWeight` other than 400 and 700 are part of the font a node asks for: one id (`glyx_text::font_id`, still at most 64 per app) covering the family, the axes and the weight, so layout, drawing, ellipsis, accessibility and the shaped-label cache all agree. The JS measuring calls take the font as their last argument: a family string, or `{ family, variations }`.
- **`fontFamily` and the `fonts` config.** A node's `fontFamily` is honoured by layout, drawing, ellipsis and accessibility on every renderer: a CSS-like list resolved to a small id (`glyx_text::family_id`, at most 64 families), part of the shaped-label cache's key, so a family never reuses another's layout. `monospace` and `serif` expand to each platform's own fonts, the default stack stays last as the fallback, and installed fonts are found by name. The new `fonts` list in `glyx.config` names font files the app ships: they are mapped (not read) and registered by every text system, and `glyx build` copies them next to the binary and stops with the file's name if one is missing. The JavaScript text-measuring calls (`__glyx_measure_text`, `__glyx_text_char_at_x`, `__glyx_text_cursor_x`, in both engines) take the family as an extra last argument, and the hit-test calls read `fontFamily` from their options, so `TextInput`, `SelectableText` and the rich-text editor place the caret by the font they draw. A `fonts` entry can be `{ src, family }` to register the file under a name of your own.
- **Colour emoji.** Emoji were drawn as flat shapes in the text colour; they now come out in their own colours on the CPU, Direct2D and Vello renderers (colour layers and colour bitmaps of the system's emoji font, such as Segoe UI Emoji). Glyphs are cached as small images under a byte limit (16 MB), ordinary text is untouched, and `GLYX_COLOR_EMOJI=0` turns it off. Not yet working: an emoji followed by the variation selector U+FE0F (the usual way to type a red heart) shows a missing-glyph box, and rotated text stays one colour.
- **A native popup menu takes a place, and works on macOS.** `glyx_tray::show_context_menu` (and `__glyx_contextmenu_show`) now takes an optional x, y in the window (physical pixels) and shows the menu there instead of at the real cursor, so a click that was injected, or came from touch or a pen, opens the menu where the app was clicked. On macOS it is shown on the window's NSView (the window's native handle is now filled in there too); this path compiles for the Apple target but has not been run on a Mac.

### Fixed
- **Video and camera were too bright on the CPU and Direct2D renderers.** Frames come out of the decoder sRGB-encoded, but were run through the "linear to sRGB" pass meant for loaded images, so every tone was lifted (a mid gray, 128, showed as 188). Live frames are now drawn as they are; a test covers it.
- **Every step that added or removed a node rebuilt the whole layout tree.** The Taffy tree was thrown away and rebuilt from the scene, and then laid out with nothing cached: about 5 ms for the 1300 nodes of a window of rows in `examples/big-table`. The layout tree is now brought in line with the scene (new nodes get a layout node, removed ones lose theirs, a container's children are reset only where they differ), so Taffy reuses what it has cached for the rows that stayed: layout of a 40 px wheel step 5.4 to 6.7 ms down to 1.0 to 1.5 ms, frame work 20 to 23 ms down to 14.5 to 16.5 ms. A full rebuild remains for the first layout, a changed root, and a tree that has collected more than twice as many layout nodes as the scene has. A test checks that the synced tree places every node exactly where a fresh build does, over seven steps of rows leaving and arriving.
- **A change inside a scrolled page repainted the whole scrolled area (CPU renderer).** The damage for a node inside a scroller that was scrolled was the scroller's whole rectangle, so a chart's hover, a blinking caret or a spinner on a scrolled dashboard repainted the entire window area (917,000 px, 22 to 28 ms for a hover in the gallery scrolled 700 px). The damage is now the node's own bounds less the scroll the scrollers around it pass on (now and where it was drawn last frame), when none of those scrollers is itself dirty, none has a transform above it and each was drawn last frame; otherwise it is the whole scroller as before. The same hover is 11,000 to 33,000 px at 3 to 5 ms.
- **Two small changes at opposite ends of the window repainted a window-sized box.** The damage merger joined any two rectangles under about 1500 px however far apart they were (a blinking caret and a hover, a clock and a spinner). Such tiny rectangles now merge only while the box around them stays under 20,000 px.
- **A 3D canvas flickered in `glyx dev` (wgpu present path).** On the overlay timer's ticks, when nothing in the scene had changed, the dev build re-blitted the cached frame, which has no 3D in it (a 3D canvas is drawn onto the swapchain image after the scene), so the 3D view vanished for that frame; in the notes app's 3D demo about a third of the frames were blank. Windows with a 3D canvas now skip that shortcut. Release builds never took it.
- **A vertical scrollbar's track slid with its thumb.** It was drawn from the thumb's top instead of the viewport's, so it was cut short at the top while scrolled; it now spans the viewport's height.
- **Images did not load on the QuickJS engine.** `__glyx_createImage` was a stub that returned 0, so `<Image>` (and `drawImage` on a canvas) showed nothing there. It now behaves as on V8: a local path must be readable under the app's `fs` capability (a `data:` or http(s) URL is not a local read), the optional size is the SVG rasterization hint, and the decode happens in glyx-core.
- **An opaque image drawn without a clip smeared over the whole CPU-rendered surface** (the rasterizer repeats an image's edge pixels outward). Canvas image draws are now always clipped to their destination; the logo in the canvas example hid it because its edges are transparent.
- **The CPU renderer's converted-image cache was limited by entry count (256), not memory.** Each entry is a full RGBA copy of an image, so 256 large images could take gigabytes. It now holds at most 64 MB, dropping the least recently used.
- **A scroller wider than the pane that clips it showed its scrollbar off-screen.** A table's row list is as wide as all its columns and sits inside a horizontal scroller; its vertical bar was drawn at the list's own right edge, which is out of sight until you pan all the way right. A scrollbar now sits on the edge you can see (the clipping ancestor's), which is also where clicks on it are tested.
- **Hot reload ran out of memory on data-heavy apps.** A reload evaluates the new bundle in the same isolate while the old app is still alive, so the live heap briefly doubles; the dev heap cap (3x the bundle size, 32 MB minimum) was too tight for an app holding a few MB of data, and V8 aborted. In dev the cap is now 3x the production one with a 128 MB floor (512 MB ceiling); production is unchanged, and `maxJsHeapMb` still overrides both.
- **The mouse wheel and touchpad scrolled the wrong way.** winit reports the direction the *content* should move; the scroll handlers (and the charts' Ctrl+wheel zoom) expect the web's convention, where a positive delta scrolls down / right. The shell now converts, so turning the wheel toward you scrolls down like every other app.

### Added
- **A complete 2D canvas** (roadmap step 9). The canvas now has a drawing state and most of what the web's 2D context has, on every renderer: `translate` / `rotate` / `scale` / `transform` / `setTransform` and `save` / `restore`; `globalAlpha`; `globalCompositeOperation` (multiply, screen, overlay, darken, lighten, difference, exclusion, and `destination-out` as an eraser); `lineCap`, `lineJoin`, `miterLimit`, `setLineDash` and `lineDashOffset` (the stroke's outline is made by kurbo in the shape's own coordinates, so it is exact under any transform); shadows (`shadowColor`, `shadowBlur`, offsets); radial and conic gradients, and gradients on strokes; shapes with several sub-paths and holes (`fill('evenodd')`); `rect`, `roundRect`, `ellipse` and `arcTo`; `drawImage` (whole, scaled, or from a source rectangle, with alpha); and PNG export, `ctx.toDataURL()` / `toPNG()`, at any scale or size up to 32 megapixels, rendered by the CPU rasterizer on any backend. The work is done once in glyx-core (`canvas_paint.rs`) and reaches Vello, tiny-skia and Direct2D as a few primitives, so the three agree; the renderers gained multi-contour fills, a blend mode and image opacity. New binary opcodes 13 to 23 and matching JSON commands. Existing drawings are unchanged (round caps and joins stay the default). Rotated, skewed and mirrored text is drawn from its glyph outlines on the CPU renderer and Direct2D (natively on Vello); upright text keeps its fast cached path. `clip()` clips to a path (even-odd or non-zero) on all three backends: a mask on tiny-skia, a shaped layer on Vello, a geometric mask on Direct2D. `getImageData(x, y, w, h)` reads a region's pixels (the export renderer, region only; up to 4 megapixels) and `toBlob()` wraps the PNG. Direct2D now has a radial gradient. Limits: the rectangular `pushClip` under a rotation is the rectangle's bounding box; Direct2D draws source-over and fills a conic gradient from wedges but a radial one ignores the inner radius; tiny-skia ignores a radial gradient's start radius; a scaled source rectangle picks up a little of the pixels beside it at its edge; a path clip on the CPU renderer builds a window-sized mask while it is open.
- **Pointer input for drawing.** The runtime keeps every cursor position a frame's merged moves passed through (`CursorMoved.trail`, up to 128 points) instead of only the last, and `Pressable` can capture the pointer (see `@glyx-dev/react`). Pen and touch pressure and tilt are not reported yet: the shell does not handle touch events, and a mouse reports 0.5 while a button is held.
- **Image export request / answer:** `SceneCommand::CanvasExport` and `InputEvent::CanvasExport`.
- **The shaped-text cache sizes itself.** Every `Text` node and canvas `fillText` string is shaped once and cached; a view with more distinct strings than the cache held (a big table, a canvas grid, a spreadsheet) re-shaped all of them every frame. The cache now starts at 256 entries, doubles while it is thrashing (evictions with more than a quarter of lookups missing) up to an 8 MB budget (4096 entries, about 2 KB each, measured with `bench_label_memory`), and shrinks back after about twelve quiet seconds, so a quiet app keeps the small size. `labelCacheEntries` in `glyx.config` (or the `GLYX_LABEL_CACHE` environment variable, which wins) pins a size instead. DevTools `Performance.getLabelCache` / `setLabelCache` show the size, fill and hit rate and pin or release it live, and the dev overlay shows `labels used/capacity (auto|pinned)`.
- **Faster JSON on the QuickJS engine.** Backend-command arguments and results no longer go through QuickJS's slow `JSON.parse` / `JSON.stringify`: arguments are written to text straight from the JS values (about 2.4x faster) and an object or array result is parsed straight into JS values (about 1.9x), with the built-in as the fallback for anything unusual (`Date`, `toJSON`, `BigInt`, cycles, odd numbers), so results and errors are the same. `__glyx_backend_call` still resolves with the string; `__glyx_backend_call2` resolves with the parsed value for a Rust command's object or array result. The websocket poll and window-size bindings build their JS values directly instead of through JSON text. V8 is unchanged. `bench_native_json_vs_quickjs` and `bench_backend_call_paths` measure it.
- **Horizontal scrolling: the `scrollOffsetX` prop.** A clipping node that carries it (even 0) shifts its children left by that many pixels, clamped to its content width, and draws a horizontal scrollbar along the bottom when the content is wider; rendering, hit testing, damage tracking and the scene cache follow the offset like they do `scrollOffsetY`. Without the prop nothing changes, however wide the content. `__glyx_getLayout` and DevTools `getLayout` report `contentWidth` for such a node, and the Inspector shows `scrollOffsetX`. `smoothScroll` eases each axis on its own spring, the horizontal scrollbar can be dragged or clicked (new `ScrollbarDragX` / `ScrollIntoViewX` events carry it to JavaScript), and focusing a node reveals it sideways as well as up and down.

### Added
- **A native popup (context) menu.** `glyx_tray::show_context_menu` shows an operating-system menu at the cursor over a window and waits for it to close (Windows; macOS and Linux report that it is not available), with submenus, check items and accelerator labels; the runtime exposes it as `__glyx_contextmenu_show(itemsJson)` / `__glyx_contextmenu_supported()` for both JavaScript engines, and `@glyx-dev/context-menu`'s `native` prop uses it. It needs no capability (it only shows the app's own choices) and is modal, like any native menu.
- **`<Camera>` works in a JS-only app.** The camera bindings were registered only when glyx-core was built with its `camera` feature, which the prebuilt runner is not ("`__glyx_camera_open` is not defined"). They always exist now; without the feature the camera is the camera capability library's, and glyx-core pulls its frames from it (capability ABI version 2: `open_sized`, `frame`) and draws, photographs and records them like a camera of its own. The camera capability library now keeps its newest frame in a swapped buffer instead of allocating one a frame.
- **Recording with sound.** A recording takes the microphone as an AAC audio track (the app needs the `microphone` capability; `{ audio: false }` turns it off), on the same clock as the video frames. `MicCapture` in glyx-sysapi is a live microphone (blocks of 16-bit samples as they are captured, whatever format the device gives).
- **Camera recording is cheaper and crash-safe.** Frames are decoded into pooled buffers shared (never cloned) by the preview, the still-photo slot and the recorder; the recorder opens its encoder on the first frame (no calibration buffer), writes each frame at its capture time (new `vm_encoder_open_timed` / `vm_encoder_write_rgba_at` in the media library), keeps a 3-frame queue and drops frames rather than piling them up, and writes a fragmented MP4, so an app that dies mid-recording leaves a file that plays up to its last second. The bit rate follows the frame size (about 0.08 bit a pixel; it was a flat 2 Mbps). With the camera's own 1280 x 720 stream and a 960 x 540 preview: recording 56% of a core at 15 frames a second and 241 MB working set before, 24% at 31 frames a second with sound and 113 MB after.
- **The preview asks the camera for a stream about its size** (`<Camera>` passes its width and height): the smallest stream at least that big at 15 frames a second or more, which also cuts decoding. A live frame at another size is scaled by a fast two-tap filter written straight into the pixmap (about 3 ms against 9.4 for a 720p frame in 960 x 540); at the same size it is copied (0.66 ms a frame).
- **The media library chooses its H.264 encoder better** (`vm_encoder_name` reports it, `GLYX_VIDEO_ENCODER=<name>` tries one first): a GPU's own encoder, then Media Foundation (it was first, and is the heaviest: 9.4 ms of CPU and +122 MB for a 720p stream against 4.6 ms and +70 MB for QuickSync), then OpenH264 (leanest, +15 MB, but built from source here so without Cisco's patent grant), then MPEG-4.
- **A release-profile runner built with glyx-core's `dev` feature honors `GLYX_MEDIA_SKIP_VERIFY=1`** (glyx-media's new `skip-verify` feature), so it can use a media library built from the source checkout; a production build never has it.
- **Much cheaper video playback.** Decoded frames go into buffers from a small pool shared with the renderer (no per-frame allocation or copy), the decoder scales to the size the video is drawn at (`vm_decoder_set_output_size`, a new optional export of the media library; older libraries decode at the source's size as before), the decoder no longer copies each frame through a buffer of its own, and the CPU renderer copies a frame that is already the drawn size row by row and otherwise fills only where the picture lands instead of the whole window. Measured with the new `examples/media-bench` on one machine (dev runner, same build, old library against new): a 1080p clip 126% to 70% of a core, 147 to 96 MB, render 64 to 2.5 ms a frame; 4K 197% to 118%, 307 to 189 MB. Camera frames take the same colour fix and copy.
- **A scroll moves the last frame's pixels instead of repainting the viewport (CPU renderer).** When a frame's only change is one plain scroller scrolling (opaque background, no radius, border, shadow, transform or opacity, whole-pixel position, nothing else painted over it), the retained frame's rows are shifted by the scroll distance and only the exposed rows, the scrollbar's thumb (new place and where the old one was) and the track's two ends are repainted (`scroll_blit.rs`; `TinySkiaRenderer::begin_frame_scrolled`). Anything else (animations, a text cursor, canvases and video in view, a second dirty scroller) falls back to the normal repaint. It also covers virtualized lists and tables (`VirtualizedList`, `DataTable`): rows that only moved in layout with the window count as content that moved with the shift, other dirty nodes inside the scroller are repainted by their own rectangles, a scroller cut off on the right by its pane is handled by its visible width, and a scroller without a background of its own works when what lies under it is flat (borders and rounded corners of the pane around it are repaired as thin strips and corner squares). On `big-table` the render of a 40 px wheel step drops from 7.2 to 5.6 ms, but presenting the shifted region costs 1.3 ms more, so the frame total is about the same there (most of it is JavaScript and layout for about 1300 nodes); window pixels are identical with the blit on and off. Scroll offsets that reach children are now rounded to whole pixels (one shared formula, `render::child_scroll_of`). In the chart gallery (release, CPU renderer) a smooth-scroll frame's render time went from about 10.4 to 4.0 ms (work 12 to 7.6 ms, present 1.5 to 3.2 ms); screenshots match the full repaint. No extra memory. `GLYX_SCROLL_BLIT=0` turns it off; `GLYX_SCROLL_BLIT_TRACE=1` says why a scroll frame was not done this way.
- **A better dev error overlay.** The overlay's stack frames in the generated bundle (`glyx://app/bundle.js:24478:34`) are mapped back to the app's own files with the bundle's inline source map (a small reader in `source_map.rs`; the map is now kept whether or not DevTools is on), and the first frame in the app's own code is shown as `srcpp.jsx:11:34` with the source lines around it and the failing line and column marked (the lines come from the map's embedded sources). **Enter** or a click on the panel opens that place in the editor (`GLYX_EDITOR` as a command with `{file}`, `{line}`, `{col}`; else `VISUAL` or `EDITOR` for VS Code and its forks, Sublime Text, JetBrains IDEs or Notepad++; else `code`; else the system default for the file); **Escape** hides the panel for that error. A successful hot reload clears it, as before. The panel is drawn in the dev overlay layer, so showing, changing or dismissing it does not repaint the app.
- **The GPU adapter probe is remembered between launches.** `RenderMode::Auto` asked wgpu what kind of GPU this is at every launch (65 to 85 ms, loading the DX12 and Vulkan drivers) even when the app then drew on the CPU. The answer is kept in `~/.glyx/cache/gpu-probe.txt`, keyed by the DXGI adapter list and the Glyx version (`GLYX_GPU_PROBE_CACHE=0` always probes): the probe falls to about 22 ms (the DXGI lookup), the first frame arrives about 76 ms sooner and the working set is about 7 MB smaller (measured on an Intel UHD 620, QuickJS exe, release).
- **`GLYX_STARTUP_TRACE=1`** prints where a launch goes, each phase's time since `main`, after the first frame (the marks are kept in memory: printing as they happen costs about 12 ms each to a redirected stderr).
- **Dev overlays no longer repaint the app (CPU renderer).** The debug overlay, the DevTools highlight, paint flashes and the error banner used to be drawn into the app's own frame, so any change to one of them (the overlay's text refresh, a highlight following the pointer, a flash fading, an overlay going away) rendered the whole window again. They are now drawn into a layer of their own, a transparent window-sized frame held only while an overlay is up (4 bytes a pixel, dev builds only), and the presenter composites it over a copy of the clean frame (`SoftPresent::present_rgba` / `re_present`). The app's frame never contains an overlay, so `overlay_was_drawn` and the forced full frames are gone on this renderer, and a DevTools screenshot is the clean frame. Direct2D and the GPU renderers still draw overlays into the app's frame.
- **A release app can start from its app precompiled.** The trailer's JS section can now hold the app compiled by the runner's own engine ahead of its source (footer flag bit 0); the runtime runs that and falls back to the source if the engine rejects it (`JsRuntime::eval_precompiled`). V8 uses its code cache, made in an isolate restored from the app's own snapshot (V8 rejects a cache made in a plain isolate): compile phase 12.7 to 0.8 ms. QuickJS, which evaluated the source on every launch, uses bytecode (`JS_WriteObject` / `JS_ReadObject` through the raw `qjs` bindings, since `rquickjs` only exposes it for modules), written without the functions' source text, which QuickJS otherwise keeps a copy of in memory. `glyx-runner --glyx-compile-js <app.js> <out>` makes it.
- **A pixel cache for canvases that are repainted unchanged.** The CPU renderer repaints only the changed part of the window, but it repaints everything that touches that part, and a canvas was repainted by running its whole drawing again (geometry, shadow copies, rotated glyph outlines) for pixels that had not changed: a chart under a gliding tooltip paid that every frame. A canvas repainted twice with the same commands is now drawn once into a bitmap and blitted on later repaints; a change to it drops the bitmap. Only where the bitmap gives the same pixels (a partial repaint, a whole-pixel position, a fully opaque node, no easing in progress, and no blend modes, eraser or images). It costs memory: 4 bytes a pixel for each cached canvas, held to a byte budget (least recently used out first; 16 MB by default; `canvasCacheMb` in `glyx.config` or `GLYX_CANVAS_CACHE_MB`; 0 turns it off) and released when the window is hidden or loses focus.

### Fixed (dev builds)
- **`glyx dev` repainted the whole window on every timer wake-up while the debug overlay was off.** A hidden overlay has no text, and its empty line list read as "first draw", so any app with a repeating timer (the charts' size check runs four times a second) redrew a full frame each time: about 4.5 full redraws a second at idle, all reported as over budget in DevTools. An idle app now renders no frames. Release builds were not affected.

### Changed
- **Nested clips on the CPU renderer cost their own box, not the whole window.** Clipping to a rounded rectangle inside another clip (a card in a rounded pane, a table in a rounded card) cloned the window-sized clip mask and walked all of it each time, about a millisecond per clip on a 1280 x 800 window: 30 rounded cards in a rounded pane took 39 ms and take 7.9 ms now. A rectangular clip inside a mask (a scroller in a rounded card) no longer clones and sweeps the whole mask either. The masks are still window-sized (tiny-skia needs that) but are made zeroed and written only over the clip's box, so the pages they touch follow the box too.
- **A partial repaint skips canvases it does not touch.** The CPU renderer already clipped draws to the changed area, but a canvas's commands were still turned into geometry first, so drawing on one canvas paid for every other canvas in the window (canvas-lab's pen next to its 12-cell grid: about 140 ms a frame in a dev build). A canvas wholly outside the repainted area is now skipped. Direct2D and the GPU renderers still repaint the whole window.
- **A canvas that eases between two drawings now eases `transform` and `globalAlpha` too** (before, a changed transform took effect at once), so content drawn under a rotation or translation, such as rotated chart labels, glides to its new place with the rest of the drawing, and a fade by `globalAlpha` is smooth.
- Scroll input carries a horizontal delta too: `InputEvent::Scroll { delta_x, delta_y }` reaches JS as `deltaX` / `deltaY`, and DevTools `Automation.scroll` / `dispatchInput` accept `deltaX`.
- **A failing async binding on QuickJS now rejects with an `Error` object**, as V8 always did, instead of the bare message string, so
  `e.message` works on both engines (and `String(e)` is `"Error: ..."` on both).
- Hot-reload rebuilds, plugin bundling and the `glyx.config.ts` fallback use the shared `glyx-bundler` (esbuild, or Bun) instead of calling Bun directly, so they work on machines without Bun, and force the JSX transform to match the React build.

### Added
- **Binary commands: `BackendRegistryBuilder::add_bytes` / `add_bytes_gated`.** A Rust command that takes the bytes of an `ArrayBuffer`,
  typed array or `DataView` and returns bytes, which reach JS as an `ArrayBuffer`: no JSON on either side. Called through
  `__glyx_backend_call2` (both engines). 4000 numbers (32 KB), release build, per call: V8 664 to 56 microseconds, QuickJS 2996 to 38.
- **`__glyx_backend_call2(name, args)`** (both engines). Like `__glyx_backend_call`, but a JS plugin command is called with the caller's
  value as it is and its result comes back untouched, instead of going through `JSON.stringify` / `JSON.parse` in both directions. A Rust
  command still takes JSON; its promise is marked `__glyxRaw` so the caller knows to parse the result. Measured with an ignored benchmark (`bench_backend_call_paths`), release build, per call, small object: JS plugin on V8 12.8 to 2.2 microseconds, on QuickJS 22.0 to 6.6 (QuickJS's floor with no native call at all is 5.6, V8's 1.1). One machine, noisy.

### Fixed
- **`fs.watch` events for a file name with a quote, backslash, newline or other control character were invalid JSON** (only `\` and `"` were
  escaped), so the JavaScript side dropped the event. Both engines now build the event with a real JSON encoder.
- The QuickJS unit-test target did not compile (a `NodeProps` test had not been updated for `smooth_scroll`, `transition_stiffness` and
  `transition_damping`); it does now, and the test feeds those props through.

## [0.2.0] - 2026-10-05

### Added
- **The app icon is available to the tray.** The window icon decoded at startup is registered with `glyx-tray`, so a tray icon created without pixels uses it, on both JS engines.
- **Native menu bar (Windows and macOS).** A `menubar` capability and `__glyx_menubar_*` bindings on both JS engines (shared logic in `glyx-runtime`'s `menubar_api`), built on `muda` in `glyx-tray`. On Windows the menu attaches to the window; on macOS it becomes the app menu with a standard application menu (About, Services, Hide, Quit) in front. The tray and the menu bar share one `muda` event handler, which routes a click to the menu bar when its id belongs there and to the tray otherwise, and cannot panic out of the window procedure. A click is pushed into the window's JS event queue (`InputEvent::MenuBar`) and wakes the frame loop, so nothing polls. The macOS path compiles but has not run on a Mac; elsewhere a native menu bar is reported as unavailable.
- **Tray events are pushed too.** `__glyx_tray_listen(true)` points tray events at the window's JS queue (`InputEvent::Tray`) instead of the polled queue. Without a listener they queue for `__glyx_tray_poll_events` as before.
- **Menu roles for assistive technology.** `menubar`, `menu`, `menuitem` and `menuitemcheckbox` map to AccessKit's `MenuBar`, `Menu`, `MenuItem` and `MenuItemCheckBox`; menu items are focusable like buttons.
- **Native keyboard focus.** Tab and Shift+Tab move focus across every focusable element (this works without the `a11y` feature), focus scrolls into view when it lands outside its nearest scroll container, and focus moves to the next valid node when the focused element is removed. The logic lives in its own `focus.rs`.
- **Accessibility hints and disclosure state.** `accessibilityHint` adds a supplementary description beyond the label, and `expanded` exposes Expand and Collapse actions for accordions and tree items.
- **`window.maxFps`** caps the frame rate of animations and drags, mainly for software renderers.
- **A motion engine owned by the frame loop.** Property transitions (timed, or on a critically damped spring that keeps its momentum when interrupted), keyframe animations, smooth-scroll springs and canvas tweens all advance in Rust, so no JavaScript runs per frame. Canvas tweens line up consecutive drawings command by command, so a chart that gains an axis tick still eases its data, and a canvas redrawn faster than its spring can settle glides linearly over the update gap instead of trailing a live stream. See ARCHITECTURE.md §24.
- **Reduced motion.** `GLYX_REDUCE_MOTION=1`, or the OS's animation-effects setting on Windows, makes transitions, smooth scroll and canvas tweens jump to their end state. Keyframe animations keep running.
- **Partial canvas redraw (CPU renderer).** A redrawn canvas is diffed against what it drew last frame and only the changed region is repainted, so a moving crosshair repaints a strip, not the chart. `GLYX_FULL_CANVAS_DAMAGE=1` turns it off.
- **Several damage rects.** A frame repaints a short list of rectangles (at most 8, merged when the box around two would waste little) instead of one box around everything that changed; the software present pushes each. `GLYX_SINGLE_DAMAGE_RECT=1` restores one box.
- **Vello scratch buffers sized from the scene.** Upstream allocates about 165 MiB of scratch buffers for every scene, sized for a 30,000-path map, and cannot recover when a scene outgrows them. They now start near 5 MiB, grow on demand and shrink when demand stays low; a frame that doesn't fit is detected from Vello's allocation counters and drawn again larger. Packaged dashboard in `renderMode: 'gpu'` on an integrated GPU: 182 MB, down from 484 MB steady and 676 MB at startup, at about +0.2 ms per frame. A scene that grows in a way the estimate doesn't see can, rarely, draw one frame with content missing before the buffers grow. `GLYX_VELLO_FIXED_BUFFERS=1` restores the fixed sizes. The Vello CPU pipeline (`renderMode: 'cpu'`) is unchanged. See `vendor/README.md`.
- **Devtools.** An Animations panel and motion-clock controls (pause, slow motion, step), GPU-renderer screenshots, and a full native DevTools suite with an MCP server (see `glyx-cli`'s changelog and `docs/DEVTOOLS.md`). `Animation.list` also reports canvas tweens and flags springs, `Automation.scroll` takes `smooth`, and `Memory.sample` includes wgpu's buffer, texture and reserved counts.

### Changed
- Consecutive cursor-move events are coalesced before they reach JS, which cuts native-to-JS traffic during fast pointer movement.
- **CPU renderer cost no longer scales with the size of the shapes drawn.** Large filled paths and long strokes are cut to the damaged region before rasterizing (tiny-skia scans a whole path before the clip mask trims it), rectangular clips stay lazy and narrow an existing mask in place instead of rebuilding a window-sized one, and glyphs, vertical gradients and large rounded rectangles have cheaper paths. A hover on the dashboard example went from about 22 ms to about 8 ms of render time.
- `glyx-sysapi` links `nokhwa` (camera) only with its `camera` feature, forwarded from `glyx-runtime`'s existing one. Builds without it no longer carry camera code. The microphone helpers are unchanged and remain in every build.
- wgpu's `counters` feature is enabled by `glyx-core`'s `dev` feature only (through `glyx-gpu`'s `counters`), since only the devtools memory panel reads it.

### Fixed
- Windows single-instance IPC used an invalid pipe path and failed with OS error 123. The pipe name now comes from one helper that builds a valid Windows named-pipe path.
- Text is measured again when its style changes, and trailing whitespace no longer leaves a line the wrong width. The text-layout cache key now includes `line_height`, so measurement matches what is drawn.
- Vello's `Scene::append` kept the wrong pending-render flags after text draws, which could skip a repaint.
